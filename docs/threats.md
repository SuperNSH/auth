# Threats and mitigations

The threat table for nsh-auth: what can go wrong in an OAuth flow on a native or web surface, which
surfaces it applies to, how this library mitigates it, and where the mitigation lives in code.

Code anchors name directories; file-level names land with the parallel build areas (core, native,
broker) and will be tightened when they do. The `z-security-auditor` pass over this code writes its
findings to [docs/security-review.md](docs/security-review.md); where that report contradicts this
table, the report wins.

| Threat | Affected surface | Mitigation | Where in code |
|---|---|---|---|
| **State mismatch** — a forged or replayed callback is injected into the app (another app can fire a custom-scheme URL on Android; a web page can redirect). Attacker completes sign-in as themselves in the victim's session. | All | Random `state` generated per request, carried in the authorize URL and compared byte-for-byte against the callback before the code is used. Mismatch → error, code discarded, no exchange. This is also why every native flow keeps PKCE: state alone proves continuity, PKCE proves possession. | Core: `crates/nsh-auth/src` and `packages/nsh-auth/src` (state generation, callback validation). Mock suite tests wrong-state rejection. |
| **Nonce mismatch** — a stolen or replayed ID token is passed off as the current sign-in. | OIDC providers (Apple, Microsoft, generic OIDC) | `nonce` in the authorize URL; after exchange, the ID token's `nonce` claim is matched before the session is created. Mismatch → reject. | Core: ID-token claim reading in `crates/nsh-auth/src` / `packages/nsh-auth/src`. Mock serves a JWKS endpoint and can mint a wrong nonce to test rejection. |
| **Authorization-code interception** — the code is observed on the way back (URL bars, other apps on the device, network). Without proof of possession it can be exchanged by the observer. | All native | PKCE with `S256`: the authorize URL carries only `code_challenge`; the `code_verifier` never leaves the app and is required at exchange. A mere interception yields an unusable code. | Core: PKCE generation and authorize-URL building; launchers pass the challenge, never the verifier, across the host boundary (`native/ios`, `native/android`, `host.call("auth.authorize", ..)`). |
| **Embedded webview exposure** — the provider's login runs inside the app's webview: the app can read everything typed, and Google blocks embedded user agents outright (`disallowed_useragent`). | iOS, Android (any surface that might embed) | The launchers never render a provider login in a webview: `ASWebAuthenticationSession` on iOS/macOS, Custom Tabs on Android — separate processes, shared cookies with the system browser, no DOM access for the app. | `native/ios`, `native/android` launcher implementations; demo buttons all route through `host.call("auth.authorize", ..)`. |
| **Redirect manipulation** — an attacker changes where the provider sends the user, or tricks the app into accepting a callback it never asked for. | All | The redirect URI is built from the app's registered provider config, not from anything user- or callback-controlled. The callback's own `redirect_uri` must match what was sent at authorize; the callback validator only accepts the exact configured URI per surface, and everything else fails closed. | Core: authorize-URL building and callback parsing in `crates/nsh-auth/src` / `packages/nsh-auth/src`. |
| **Secret embedding** — a client secret ships inside an app bundle and is extracted from the binary. | All apps; acute for GitHub, whose exchange requires a secret | No secret is ever passed to either core. Confidential exchanges go through `tools/broker`, deployed by the app owner, secret only in the broker's environment. A build-gate test greps app build output for secret material. | `tools/broker` (secret handling); core provider definitions (no secret field reaches an app); setup steps in [docs/setup.md](docs/setup.md#github-and-the-token-broker). |
| **Loopback port squatting** — on desktop, a local attacker pre-binds the port the app will use, receives the provider's redirect, and harvests the code. | Windows, Linux (and macOS if loopback is used) | The listener binds `127.0.0.1` only (never a routable interface), picks a random free port, accepts a single authorization code, validates `state` against the in-flight request, and shuts down immediately after. A squatter holding the port beforehand makes bind fail loudly rather than silently degrading. | Desktop launcher area (system-browser + loopback path), on top of the core's state validation in `crates/nsh-auth/src`. |
| **Token leakage via logs** — access or refresh tokens printed by debug logging end up in consoles, crash reports, or `.nsh/tui.log`. | All | Tokens are carried in values that never implement debug/print paths that expose them; error types name the failure without embedding response bodies; the audit pass greps log call sites for token material, and the device proofs check logs after sign-in (brief criterion 6). | Core session/token types and error types in `crates/nsh-auth/src` / `packages/nsh-auth/src`; verified by the `z-security-auditor` pass ([docs/security-review.md](docs/security-review.md)). |
| **Storage compromise** — tokens end up in plain storage readable by anything running as the user. | All | Sessions are persisted only through the secure-store path per platform: Keychain on iOS/macOS, Android Keystore, the desktop/desktop-web equivalents. Plain `Storage` is never used for tokens, and the storage proofs confirm absence from plain files and logs after a restart. Honest limit: the desktop store is a `0600` file under the user's profile — protected from other users, **not** from the user themselves or any process running with their privileges; it is not Keychain-grade. | Session store trait in the cores; per-platform implementations in `native/ios`, `native/android`, and the desktop launcher area. |
| **Refresh-token theft and replay** — a copied refresh token is used elsewhere, or a revoked token keeps a dead session alive. | All | Refresh tokens live only in the secure store; refresh runs single-flight (parallel calls share one request, so a leak window isn't widened by concurrent refreshes); sign-out revokes server-side via the provider's revoke endpoint; a revoked-refresh response ends the session instead of retrying. | Core: refresh and single-flight logic, sign-out with revocation in `crates/nsh-auth/src` / `packages/nsh-auth/src`. Mock suite covers refresh, single-flight, and revoked-refresh rejection. |
| **Custom-scheme callback hijacking** — on Android, any installed app can fire the demo's `nsh.auth.sandbox://` intent. | Android (and iOS apps with registered schemes) | Treated as the state-mismatch row's delivery vehicle: the hijacker can deliver a URL, but cannot forge a matching `state` for an in-flight request nor pass the PKCE exchange. The intent filter also checks the exact host/path shape. | `native/android` intent filter; core callback validation as above. |

## What this table does not claim

- It assumes the device is not rooted and the provider itself is honest; a rooted device defeats
  the Keychain/Keystore threat model, and a malicious provider is out of scope by definition.
- Phishing is unchanged by any of this: the system browser still shows the provider's real page,
  and nothing here stops a user from typing credentials into a fake one.
- The desktop `0600` file store is a deliberate, documented compromise (see the storage row), not
  an oversight; replace it if your threat model includes hostile processes running as the user.
- Mitigations are code-level claims; the standing evidence for them is the mock suite's
  negative-path tests and the `z-security-auditor` report, not this document.
